# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Galactic Guardian is a 2D top-down space shooter built with **pygame-ce** and **pygame_gui**. The window is a fixed 600x800. Code, comments, identifiers, and docstrings are in **Spanish** — follow that convention when adding code.

## Commands

```bash
# Setup (Windows)
python -m venv venv
.\venv\Scripts\activate
pip install -r requirements.txt

# Run the game (from the repo root)
python main.py

# Tests (headless; conftest.py forces the SDL dummy drivers)
pip install -r requirements-dev.txt
pytest
pytest --cov --cov-report=term-missing
pytest tests/test_input.py::test_escape_pausa_y_reanuda   # a single test
pytest tests/test_engine.py -k transicion                 # by keyword
```

`requirements.txt` pins `pygame-ce==2.5.8` and `pygame-gui==0.6.14` (note: `pygame-ce`, not vanilla `pygame`). `requirements-dev.txt` adds `pytest` + `pytest-cov`. `pyproject.toml` holds the pytest/coverage config and `version`. CI (`.github/workflows/ci.yml`) runs the suite on Python 3.11–3.13 and refreshes the coverage badge; `main` is branch-protected (PR + green CI required). No linter is configured. See `CONTRIBUTING.md` for the workflow and release process.

## Runtime data & config (gitignored)

`.gitignore` excludes `/config.ini` and `/data/saves/`, so these files exist only locally and are recreated on demand:
- `config.ini` — persisted music/effects volume (`[VOLUMEN]` section), the screen-shake and damage-number switches (`[PANTALLA]`: `temblor`, `cifras_dano`, both `si`/`no`, on by default) and rebindable controls (`[CONTROLES]`, one key name per action), read/written by `src/core/config.py`.
- `data/saves/progresion.json` — coins and bought upgrades (`Progresion`, see "Progression between runs").
- `data/saves/partida_campana.json` and `data/saves/partida_sin_fin.json` — the saved-game checkpoint of each mode (`Guardado`, see "Saved game").
- `data/saves/puntuaciones.json` (campaign) and `data/saves/puntuaciones_sin_fin.json` (endless mode; `SistemaClasificacion(nombre_archivo=...)`, one instance per mode, never mixed) — high-score tables, managed by `SistemaClasificacion` (`src/ui/scoreboard.py`): `{nombre: {"puntos": N, "nivel": M}}` (`nivel` = how far the run got). Reads accept the old plain-`int`-per-name shape too (`nivel` comes back as `None`); a name only gets rewritten to the new shape when its score improves. `obtener_puntuaciones_top()` returns `(nombre, puntos, nivel)` triples.

Path resolution goes through **`src/core/paths.py`** (`src/core/version.py` holds `__version__`, kept in sync with `pyproject.toml`):
- `paths.recurso(...)` → read-only bundled assets. Dev: project root. Frozen (PyInstaller): `sys._MEIPASS`.
- `paths.dir_datos_usuario()` → writable dir for `config.ini` + saves. Dev: project root (paths are now absolute, so the CWD no longer matters). Frozen: the OS user-data dir (`%APPDATA%\GalacticGuardian`, `~/Library/Application Support/…`, `~/.local/share/…`) so user data survives an app-folder replace and works from a protected install path.

Assets live under `data/assets/` (`imagenes/`, `musica/`, `sonidos/`). Logical asset names map to relative paths in `src/core/config.py`: `RECURSOS` (images) + `HOJAS` (sprite sheets, below), `SONIDOS` (short SFX, loaded into RAM as `mixer.Sound`), and `MUSICA` (background tracks — the raw OGG **bytes** are read into RAM at startup and played with `mixer.music.load(BytesIO(...))`; still decoded on the fly, not decompressed). Add new assets to the right dict, not by hardcoding paths.

**Sprite sheets** (animations): one PNG holding every frame in a regular grid — equal cells, no margins between them, read left→right then top→bottom. `config.HOJAS` maps a name to `{"ruta", "columnas", "filas", "cantidad"}` (`cantidad` = how many cells are real when the last ones are empty; optional); `main.cargar_activos_del_juego` loads each with `ResourceManager.load_spritesheet(name, path, columnas, filas, cantidad)` (raises `ValueError` if the sheet doesn't divide into equal cells or `cantidad` doesn't fit) and consumers ask for the frames with `rm.get_frames(name, size=None)` — a fresh list each call, scaled to `size` and cached like `get_image_scaled`, `[]` (plus a console error) for an unknown name. The explosion is the first one (`"explosion"`, 4×3 cells of 128×128, 11 frames, in `data/assets/imagenes/explosion/explosion.png`; `EffectManager` scales it to 64×64); `Explosion` only takes a list of frames, so it doesn't care where they come from. A sheet with several animations (e.g. one per row) isn't supported yet: it'd need choosing a row/range in `get_frames`.

Tunable gameplay/loop constants (window size, FPS, invuln/contact windows, damage/health balance) live in `src/core/settings.py`. **What each level contains** does not: it lives in `src/core/niveles.py`.

**Texts / i18n** (`src/core/i18n.py`): every user-visible string goes through `t("namespace.key", **datos)`, never a literal in a screen. Each language is a flat JSON in `data/assets/idiomas/<code>.json` (bundled with the rest of `data/assets/`, so no `.spec` change); **Spanish (`es`, `i18n.REFERENCIA`) is the reference** — every key exists there and it is the fallback when another language lacks one, and a key missing everywhere returns the key itself (`t()` never raises). Placeholders are `str.format` (`"Nivel {n}"`, `t("...", n=3)`). `i18n.establecer_idioma(code)` sets the current language (module state, doesn't touch `config.ini`). Available languages are `i18n.IDIOMAS` (`es`, `en`) with their own-language names in `i18n.NOMBRES`. At startup `main.py` uses `config.cargar_idioma()` (`[IDIOMA] codigo` in `config.ini`, `None` if absent/invalid) or, the first time, `i18n.detectar_idioma_sistema()` (Windows UI language via `GetUserDefaultUILanguage`, else `LC_ALL`/`LANG`/locale; English if it's English, otherwise Spanish). In Opciones, the "Idioma" tab has one `UIButton` per language (the current one `.select()`ed); `MenuManager._cambiar_idioma` applies it **instantly** and it's written to disk only on Guardar, like volume. Because button texts are cached, switching rebuilds them: the main-menu `Boton`s right away (`_crear_botones`, which also records `_idioma_botones` so a *persistent* menu notices, in `ejecutar()`, that the language changed elsewhere), the Opciones UI, which records the language it was built in (`_idioma_ui`) and is rebuilt by `_abrir_opciones` / at the start of `_menu_opciones` whenever that no longer matches the current one (never mid event-loop, since the loop still holds the old elements; and it also covers the *persistent* menu whose Opciones were built before the language changed from a pause), and — when Opciones was opened from a pause — `Juego._invalidar_botones()` resets every cached overlay button to `None` so `RenderManager` recreates them. Not translated on purpose: `print`/console messages, the F1 debug overlay (FPS, `t:`, stat numbers) and the docs. Action names go through `controles.etiqueta(accion)` and key names through `controles.nombre_tecla()` (`"Espacio"` is a catalog entry). `tests/conftest.py` forces `es` for every test; `tests/test_i18n.py` checks that every `"namespace.key"` literal used in `src/` exists in `es.json`.

**Level definitions** (`src/core/niveles.py`, pure data): `NIVELES` is a tuple of `DefinicionNivel` — one per campaign level, exactly `settings.NIVEL_MAX` (a test enforces it) — with `fases` (`Fase(desde_ms, enemigos)`; `enemigos` is a tuple of enemy classes picked uniformly, repeat a class to weight it), `tiempo_jefe_ms`, `espera_jefe_ms`, `intervalo_spawn` `(min, max)`, `jefe` (class), `musica` and `musica_jefe`. Adding or retuning a level means editing that table; `WaveManager` and `Juego` only read it via `definicion_nivel(n)` (clamps out-of-range `n`). The values are literals, not derived from a formula. Enemy health and damage by level are **not** in this table but in `src/core/escalado.py` (see "Real health and damage numbers"): the entities read them, and `niveles.py` imports the entities, so they can't live here. Entity-local constants stay on their class (`Jugador.CONFIG`, `EnemigoBase.TAMANO_ESTANDAR`, `Bala.TAMANO`, …).

## Architecture

### Entry point & state flow

`main.py` initializes pygame, builds the singleton `ResourceManager`, loads every asset up front (`cargar_activos_del_juego`), builds one shared `AudioManager`, then runs a **top-level state machine**: `estado` cycles between `"MENU"` and `"JUGAR"` / `"CONTINUAR"` / `"JUGAR_SIN_FIN"` / `"CONTINUAR_SIN_FIN"` (campaign / endless mode, which builds `Juego(..., modo=settings.MODO_SIN_FIN)` with the endless ranking; the `CONTINUAR*` ones pass `continuar=True`, the plain ones first `borrar()` that mode's saved game) until `"SALIR"`. `MenuManager.ejecutar()` and `Juego.ejecutar()` each run their own loop and **return the next state string** — they never instantiate each other or call `sys.exit()`. `MenuManager` (`src/ui/menu.py`) is itself a sub-state machine (`PRINCIPAL` / `OPCIONES` / `PUNTUACIONES` / `MEJORAS`); its persistent instance is reused each time control returns to the menu (`ejecutar()` resets its own state on entry).

Exit routing: the window's X button → `"SALIR"` (app quits after `pygame.quit()` in `main.py`); "Salir" from pause (after the confirm dialog) and "Salir" on Game Over → `"MENU"`. `Juego` exposes `volver_al_menu()` / `salir_del_juego()` which just set `self.resultado` + `self.ejecutando = False`. The main menu has its own **Salir** button with the same kind of confirm dialog (`MenuManager._confirmar_salida`, a self-contained blocking loop — the menu has no `UIManager` to share the in-game one with); confirming, or closing the window while the dialog is up, both return `True`.

`engine.py` still imports `MenuManager` function-locally in `mostrar_opciones_juego` (pause → options opens a throwaway `MenuManager` sharing the same `AudioManager`); `menu.py` no longer imports `engine`. **Options: preview / Volver / Guardar.** Changes to volume, language and keys apply **instantly as a preview** (you hear/see them), but only **Guardar** confirms them (they stay for the session *and* go to `config.ini`); **Volver — or closing the window — discards them**. `_abrir_opciones()` (the entry point from the main menu *and* from a pause) takes a snapshot (`_instantanea`: live volumes from the `AudioManager`, current language, copy of the key map) and `_deshacer_cambios()` restores it (volumes through the `AudioManager`, language via `establecer_idioma` + `_crear_botones`, keys). Rebuilding the Opciones UI after a language change goes through `_preparar_ui_opciones()`, **not** `_abrir_opciones()`, precisely so the snapshot isn't retaken mid-visit (a test covers it). Invariant this gives: outside an Opciones visit, the live state always equals what's on disk (or what was confirmed), which is why `_sincronizar_estado()` below is enough to keep the persistent menu correct.

Because there are **two** `MenuManager` lifetimes (the persistent main-menu one and a throwaway per pause), what Opciones shows must never come from state captured at construction: `MenuManager._sincronizar_estado()` re-reads it from the source of truth — volumes from the shared `AudioManager` (what's actually playing; unsaved slider changes take effect immediately but only hit `config.ini` on Guardar), keys from `config.ini` (what every new `Juego` reads) — in `__init__` and at the start of `ejecutar()` (each return to the main menu). Language works the same way through `_idioma_ui` / `_idioma_botones`. Otherwise Guardar in the main menu would overwrite, with stale values, what was changed from the pause.

### The `Juego` "god object" + manager pattern

`Juego` holds all match state (score, level, `pausado`, `estado_game_over`, `pidiendo_nombre`, sprite groups, difficulty timers) and delegates behavior to managers. Audit item 14 (shrinking the god object) is largely done: the **mechanical** managers now take explicit collaborators, the **view/controller** ones still take `juego` by design (see "Still open" below).

- Explicit deps, no `juego` reference: `WaveManager(rm, am, ancho, alto)`, `EntityManager(rm, ancho, alto, enemigos_golpeados)`, `EffectManager(rm, entity_manager, jugador)`, `CollisionManager(entity_manager, jugador, effect_manager, audio, enemigos_golpeados, reglas)`. This works because the identities they capture (`jugador`, `enemigos_golpeados`) are stable across `reiniciar_juego` (reset in place / `.clear()`ed, never rebound).
- `CollisionManager`'s `reglas` **is** the `Juego` — but a named narrow role, not attribute access: the manager only calls `reglas.al_eliminar_enemigo(enemigo)` (score, combo, boss transition) and `reglas.manejar_impacto_jugador()` (flash / death / respawn). Everything mechanical (collide, `take_damage`, `kill`, explosion, cooldown bookkeeping, SFX, `item.aplicar_efecto`) stays in the manager.
- Still take `juego` by design: `InputHandler`, `RenderManager`, `UIManager` — the view + controller layer. They legitimately observe the whole match; they only *write* UI flags (`pausado`, `debug_hitboxes`, `nombre_entrada`, cached overlay buttons).

- **`InputHandler`** (`src/core/input.py`) — translates pygame events into `Juego` method calls; owns the pause/game-over/name-entry input modes and the blocking quit-confirmation dialog (which now `tick(30)`s to avoid a CPU-spin). `manejar_eventos()` returns `False` to end the game loop; `QUIT` sets `salir_del_juego()` rather than killing the process. Continuous fire is a flag (`juego.disparando`) polled each frame. `self.mapa_teclas` (loaded via `config.cargar_controles()` at construction) holds the reassignable key for movement/disparar/pausa; `_manejar_teclas_presionadas` checks `tecla == self.mapa_teclas["pausa"]` / `["disparar"]` instead of hardcoded keys. Arrow keys and Esc are **not** in the map — they're hardcoded fixed fallbacks (in `InputHandler` for pause, in `Jugador.mover` for movement) so a bad rebind can never lock the player out of moving or pausing.

- **Rebindable controls** (`src/core/controles.py` for the pure logic — `ACCIONES`, `ETIQUETAS`, `POR_DEFECTO` (WASD + Space + P, matching what used to be hardcoded), `nombre_tecla()` — and `config.cargar_controles()` / `guardar_configuracion(..., mapa_controles=...)` for persistence, same `config.ini` file, `[CONTROLES]` section, one key name per action via `pygame.key.name()`/`key_code()`, each action falling back to its own default independently if its stored name is missing/invalid). `Jugador.mover(teclas, pantalla, dt, mapa_teclas=None)` ORs each direction's fixed arrow key with `teclas[mapa_teclas[accion]]` (defaults to `controles.POR_DEFECTO` if not passed, so callers that don't care about rebinding still work). In Opciones, the "Controles" tab has one `UIButton` per action showing `"Etiqueta: Tecla"`; clicking one sets `self._reasignando_accion` and the next `KEYDOWN` — intercepted before the normal pygame_gui event handling — either cancels (Esc), rejects with a timed on-screen warning if the key is already used by a *different* action (`self._aviso_conflicto`), or applies it to `self.controles` (a plain dict, not yet written to disk) and updates the button's text. "Restaurar valores por defecto" resets `self.controles` to `controles.POR_DEFECTO` the same (in-memory) way. Nothing touches `config.ini` until **Guardar** (see "Options: preview / Volver / Guardar" below). A rebind has no live singleton to push into (unlike volume, which mutates the shared `AudioManager` on every slider move), so `mostrar_opciones_juego()` (`engine.py`) copies the throwaway `MenuManager`'s `menu.controles` into `self.input_handler.mapa_teclas` right after `mostrar_solo_opciones()` returns: the new keys after Guardar, the previous ones after Volver (which restored them). A fresh `Juego` always reads `config.ini` via `InputHandler.__init__`.
- **`EntityManager`** (`src/managers/entities.py`) — owns four `pygame.sprite.Group`s: `balas`, `balas_enemigo`, `enemigos`, `efectos` (explosions + destellos). `actualizar(dt, tiempo_juego)` updates every group, drives enemy/boss auto-fire (needs the clock for their cadences), and `kill()`s off-screen entities. There is **no `juego.all_sprites`** anymore; the player is a lone `Sprite` held on `juego.jugador`.
- **`CollisionManager`** (`src/managers/collision.py`) — `actualizar(tiempo_juego)`. Detection via `pygame.sprite.groupcollide` / `spritecollide`. Bullets↔ships use `collide_circle` (needs `sprite.radius` — the attribute is `radius`, not `radio`); body contact and item pickup use rect collision (`CONTACTO_COOLDOWN_MS` per-enemy cooldown in `enemigos_golpeados`, a `WeakKeyDictionary` also purged explicitly on death/despawn). `_eliminar_enemigo` guards against double-processing when several bullets kill one enemy in a frame, then hands off to `reglas.al_eliminar_enemigo`. Boss death → `Juego.al_eliminar_enemigo` sets `pendiente_reinicio = True`; the actual `reiniciar_juego()` runs at the end of `Juego.actualizar()` (never mid-collision).
- **`WaveManager`** (`src/managers/waves.py`) — time-based spawn director with **no level logic of its own**: it reads `niveles.definicion_nivel(nivel)` (see "Level definitions" below) and picks the last `Fase` whose `desde_ms` has been reached, then a uniform `random.choice` from that phase's `enemigos`; once `tiempo_jefe_ms` is reached it swaps to the level's boss music and, after `espera_jefe_ms`, returns the level's boss class. Each enemy class carries its own sprite name in `RECURSO`, which is what it asks `ResourceManager` for.
- **`RenderManager`** (`src/managers/render.py`) — orchestrates all per-frame drawing. Real pause takes a fast path: on the first paused frame it snapshots `pantalla`, multiplies it to grey once (`_frame_pausa`), and just re-blits that + text + buttons until unpaused (any active-game render resets `_frame_pausa`). Game Over / name-entry set `juego.pausado = True` too but are excluded from that path and get their own overlay. Overlay buttons (`boton_reintentar`, `boton_salir_post`, `boton_opciones`, `boton_salir`) are created **once**, lazily, and cached on `juego`; `InputHandler` reads those attributes. Fonts are built in `__init__`. `Boton` caches its own rendered `Surface`.
- **`EffectManager`** (`src/managers/effects.py`) — explosions and screen flashes (`src/visual/`); adds them to `entity_manager.efectos`. It also owns the **screen shake** (`self.temblor`, a `Temblor` from `src/visual/screen_shake.py`): a trauma model (0..1) where `agregar_temblor(x)` adds trauma (capped at 1), `Juego.actualizar(dt)` decays it by `TEMBLOR_DECAIMIENTO`/s on the game clock (so it freezes in pause; it runs before the `transicion_activa` branch so it also decays during the level-end transition), `reiniciar_juego` zeroes it, and `RenderManager._aplicar_temblor()` shifts what's already drawn (background, entities, ship) by `TEMBLOR_MAX_PX * trauma² * random(-1..1)` per axis — *before* the HUD, which therefore stays put, and only on the live-game path (Game Over / level-complete / pause overlays don't shake). It re-blits a copy of the screen over itself without clearing, so the border strips show the unshifted frame rather than black; it costs ~0.4 ms and only while shaking. Triggers: an impact on the ship (`TEMBLOR_GOLPE`, skipped while invulnerable), losing a life (`TEMBLOR_MUERTE`) and defeating the boss (`TEMBLOR_JEFE`), all from `Juego`; ordinary enemy kills do **not** shake (endless mode would be constant). **It can be switched off** from Opciones' "Pantalla" tab (`preferencias.temblor_activado()` in `src/core/preferencias.py`: module state like `i18n`; `main.py` sets it at startup from `config.cargar_temblor()` — `[PANTALLA] temblor = si/no` in `config.ini`, on by default): `agregar_temblor` ignores requests when off and `desplazamiento_temblor()` also reads the flag, so turning it off mid-shake cuts it. It follows the usual Opciones semantics (instant preview, kept in `_instantanea`, Volver discards, Guardar writes `temblor=` through `guardar_configuracion`, and `_preparar_ui_opciones` re-reads it so another `MenuManager` sees the live value). `tests/conftest.py` resets it to on for every test. A hit-stop (freezing the game a few frames on heavy hits) was tried and dropped: see ROADMAP "Descartado". **Floating damage numbers** (`src/visual/floating_text.py`, `CifraFlotante`; `EffectManager.crear_cifra_dano(objetivo, posicion, danio, de_la_nave=False)`): a number with a dark outline that enters with a **pop** (born at `CIFRA_POP_INICIO` scale, overshoots to `CIFRA_POP_MAX` and settles at 1 within `CIFRA_POP_MS`; summing more damage into it replays a milder pop), rises `CIFRA_VELOCIDAD` px/s and fades over `CIFRA_DURACION_MS`, living in `entity_manager.efectos` (so it moves with the game `dt` and freezes in pause). `CollisionManager` creates one per player bullet that hits an enemy (yellow, at the bullet's `midtop`) and one when damage really reaches the ship (red, larger; through `_danar_jugador`, only if `recibir_danio` returned True, i.e. not invulnerable; both bullets and contact). The enemy's own contact damage (`DANIO_EMBESTIDA`) also shows a number, **even with the ship invulnerable** (the enemy takes that hit regardless). Hits on the same target within `CIFRA_COMBINAR_MS` are **summed into one number** (a triple shot, or a burst on the boss; `_cifras` is a `WeakKeyDictionary` target → latest number) and there is a cap of `CIFRAS_MAX` live ones, otherwise 8 shots/s × 3 bullets would bury the screen. They can be switched off from Opciones' "Pantalla" tab like the shake (`preferencias.cifras_dano_activadas()`, same preview / Volver / Guardar semantics, `guardar_configuracion(..., cifras_dano=...)`, `config.cargar_cifras_dano()`; `conftest.py` resets it to on).
- **`UIManager`** (`src/ui/hud.py`; the HUD always shows the ship's health as numbers, `hud.salud` "SALUD: 87/150" under the lives — `ceil` of the current health since regeneration makes it fractional, red below `SALUD_BAJA` = 30 % — because the bar under the ship has a fixed width and says nothing about the amount) — HUD and overlay text/box drawing.
- **`AudioManager`** (`src/core/audio.py`) — music/effect playback and volume. **One instance**, built in `main.py` and injected into both `MenuManager` and `Juego`. Music: one track at a time via `pygame.mixer.music`, loaded from the in-RAM OGG bytes (`get_music_data` → `BytesIO`) so a track switch never stalls the main loop. `reproducir_musica(nombre)` is idempotent (no-ops if `nombre == pista_actual`) and fades the new track **in**; `detener_musica`/`detener_toda_la_musica` do a hard `music.stop()` — **not `fadeout()`**, because a pending fadeout makes the next `music.load()` block until it finishes (~200-300 ms hitch). Effect names in code (`"disparo"`, `"golpe"`) are aliases over the `SONIDOS` keys (`laser_gun`, `hit`). `main.py` calls `pygame.mixer.pre_init(44100,-16,2,512)` before `pygame.init()` and bumps to 16 channels.

### Game loop (`Juego.ejecutar`)

Each frame: `input_handler.manejar_eventos()` → if `pausado`, draw only → else compute `dt = min(reloj.tick(FPS)/1000, 3/FPS)` and `actualizar(dt)` (player move, spawn check, `entity_manager.actualizar(dt)`, `collision_manager.actualizar()`, background) → `dibujar()`.

**Delta time**: all movement is FPS-independent. Speeds are still expressed in px/frame-at-60fps; `MovimientoSubpixel._desplazar(vx, vy, dt)` (`src/entities/base/movimiento.py`) multiplies by `dt*FPS` and carries the sub-pixel remainder so fractional speeds aren't lost to the integer `rect`. The `rect` stays the source of truth, so code that repositions it directly (respawn, boss bounce) doesn't desync. At exactly 60 FPS behaviour is identical to the old frame-based code.

**Game clock**: `Juego.tiempo_juego` (ms) is a monotonic clock that **only advances inside `actualizar(dt)`** (`self.tiempo_juego += dt*1000`). Since `actualizar` isn't called while `pausado` / game over, it freezes on its own — no manual pause bookkeeping. All game-logic time reads `juego.tiempo_juego`, never `pygame.time.get_ticks()`: cadences (`jugador.ultimo_disparo`, `enemigo.tiempo_ultimo_ataque`, `jefe.ultimo_disparo_*`), invulnerability deadline, wave-phase clock (`ahora - inicio_juego`), boss-wait (`WaveManager._procesar_fase_jefe(tiempo_juego)`), and the `enemigos_golpeados` contact-cooldown timestamps. `pausar_juego`/`reanudar_juego` only flip `self.pausado`. `Jugador.update(dt, tiempo_juego)` and `WaveManager.spawn_enemigo(tiempo_nivel, tiempo_juego, ...)` take the clock. `reiniciar_juego` resets `tiempo_juego`/`inicio_juego` to 0 and the player's timers. Any new time-gated behavior must read `juego.tiempo_juego` or be dt-based.

**Restart (`reiniciar_juego(nivel_forzado=None)`)**: three paths, chosen by `nivel_forzado` then `jefe_derrotado`. Level advance (`jefe_derrotado`, no `nivel_forzado`) keeps the same `Jugador` and its upgrades, bumps `nivel`, re-centers it with `Jugador.recentrar(ancho, alto)` (position + sub-pixel accumulators only; `reiniciar_juego` then heals the health bar to full with `curar(salud_maxima)`, but upgrades and remaining lives are kept — the level-end transition, below, leaves the ship off-screen), and `EntityManager.vaciar_todo(avance_nivel=True)` clears only enemies — **every projectile (player and enemy bullets) and effect already in flight survives** so nothing pops out on boss death (the transition itself already cleared bullets earlier; see below). Full restart (`nivel_forzado=None`, no `jefe_derrotado`) and level-select (`nivel_forzado=N`, from the campaign's level-select screen) both reset the `Jugador` **in place** via `Jugador.reiniciar(ancho, alto)` (same instance — managers may hold the reference; audit item 14), zero `puntuacion`, and `vaciar_todo()` clears everything; level-select additionally sets `self.nivel = nivel_forzado` directly. `enemigos_golpeados` is `.clear()`ed, never reassigned, for the same reason. Spawn cadence and music for `self.nivel` come from `niveles.definicion_nivel(nivel)` — a pure lookup by level number (not iteratively-decremented state), precisely so level-select can jump straight to the right difficulty. `reiniciar_juego` also resets `self.background.velocidad` to `settings.FONDO_VELOCIDAD_NORMAL` and clears any leftover transition state, in case it's ever called while one was active.

**Progression between runs** (`src/core/mejoras.py` = data, `src/core/progresion.py` = state): `mejoras.MEJORAS` is a table of 30 `Mejora`s — three branches of ten (`RAMAS`: ataque, defensa, utilidad), each unlocked by buying the previous one (`requiere`) — whose `efecto` is a dict of `Bonus` fields; `calcular_bonus(ids)` folds them into a frozen `Bonus` (numbers add, `combo_factor` multiplies). Ataque: damage +5 four times, +1 shot/s four times, +1 bullet twice (double, then triple) — the last four nodes (`ataque_7..10`, 2000–3100 coins) are the late-game power that takes damage and fire rate to their caps (30 / 8); Defensa: health +15/+15/+20/+25/+25, +1 life twice, regeneration 0.5/s twice, +2 s respawn shield (`defensa_7..10` are the late-game ones); Utilidad: speed +0.25 four times (Motores I–IV, shown as "+5 % de velocidad" — 5 % of the base 5 — and reaching the cap of 6 exactly; **no more speed nodes on purpose**), coins +25 % three times and +50 % once (Botín I–IV, +125 % total — the tail of the tree is expensive), an easier combo twice (Maestría I–II, ×0.8 each). The ship starts at 50 health, 3 lives, 10 damage, speed 5, 4 shots/s, 1 bullet; caps in `Jugador.CONFIG`: speed 6, 8 shots/s, 3 bullets, 30 damage. Bonuses raise the **starting** values, never those caps: `Jugador(imagen, ancho, alto, bonus=None)` keeps `self.bonus` and `reiniciar()` applies it (`disparos_s` is shots per second — `cadencia_disparo` is derived in ms —, `balas_por_disparo` is 1–3, `regen_s` health per second), which is why every restart path keeps it. **Regeneration**: `Jugador.update` recovers `regen_s` per second once `settings.JUGADOR_REGEN_ESPERA_MS` (3 s) have passed since the last hit that landed (`marcar_golpe`, called from `Juego.manejar_impacto_jugador` only when not invulnerable); it never revives a ship at 0. `Juego` also uses the bonus for the respawn-shield length (`invulnerable_extra_ms`) and `Combo(factor)` scales `COMBO_UMBRALES`. The save file has a `version` (`progresion.VERSION_ARCHIVO`, now 2): a version-1 (or unversioned) save comes from the old 12-node tree, so loading it **refunds what it cost** (`_COSTES_V1`) and starts with an empty tree. `Progresion(ruta=None, persistir=True)` holds `monedas` and `compradas` and saves `data/saves/progresion.json` (`{"version", "monedas", "mejoras"}`) on every change, atomically (temp file + `os.replace`); loading is tolerant: an unreadable/ill-typed file is copied to `.corrupto` and it starts empty, unknown ids and negative coins are dropped, and a purchase whose `requiere` isn't owned is discarded with its cost refunded. `Mejora.icono` optionally names an image from `config.RECURSOS` (the old item icons: `potenciador_danio`, `potenciador_cadencia`, `potenciador_velocidad`, `curacion`) that `MenuManager._icono_mejora` draws, cached and dimmed while locked, in the node's top-right corner. `comprar(id)` returns `OK` / `YA_COMPRADA` / `BLOQUEADA` / `SIN_SALDO` / `DESCONOCIDA`; `restablecer()` refunds **everything** spent for free. `main.py` builds one `Progresion` shared by `MenuManager` (where it is bought) and every `Juego(..., progresion=...)` (which reads the `Bonus` at construction, so a new `Juego` per run picks up new purchases); `None` means no progression (tests, the pause's throwaway menu uses an in-memory one). **Coins** come from the score: `Juego._cobrar_monedas()` ingests `int(puntuacion // settings.MONEDAS_PUNTOS * (1 + bonus.monedas_pct))` minus `monedas_cobradas`, so it is idempotent and is simply called at every point where progress could be lost — Game Over/victory (`_pedir_nombre_o_mostrar`, which is what the final screens show: "+N (total M)"), each campaign level end, `volver_al_menu`, `salir_del_juego`, the end of `ejecutar()`, and at the top of `reiniciar_juego` on the paths that zero the score (which then also zero `monedas_cobradas`; a level advance keeps both). The main menu has a sixth button, **Mejoras** (title + six buttons are re-centred as one block, update banner below), opening `MenuManager` state `"MEJORAS"`: `_menu_mejoras()` draws the three columns in a **scrollable area** (`_MEJ_AREA`; `_rects_mejoras` are precomputed from `_rect_mejora` in *content* coordinates, the first node at y = 0, and `_rect_pantalla(id)` shifts them by `_scroll_mejoras`; the nodes are drawn clipped to the area so they never cover the branch headers or the buttons, and a node is only clickable while it is inside the area). It scrolls with the mouse wheel (`MOUSEWHEEL`, `_MEJ_PASO_RUEDA` px per notch), a scrollbar you can drag or click (`_rect_barra`, only drawn when the tree is taller than the area), the arrow / PageUp / PageDown / Home / End keys, or **dragging the content with the mouse held down** (touch-style, `_arrastrar_contenido`: it follows the pointer once it has moved `_MEJ_UMBRAL_ARRASTRE` px; because of that a node is bought on **release** of a press that never became a drag — `_comprar_en` from `_evento_mejoras` — not on press), and `_abrir_mejoras` resets it; **debug**: when running from source (or with env `GG_DEPURACION`; `paths.es_desarrollo()`, never in the frozen build) **F2** in this screen adds `MONEDAS_DEPURACION` (1000) coins and a red "DEBUG" hint is drawn — note it writes to the real `progresion.json`; the tree can therefore have as many nodes per branch as needed, a node click buys (`_clic_mejoras`, timed notice on no-funds/locked), **Restablecer** refunds and **Volver**/Esc leaves. Costs, effects and the coin rate (`settings.MONEDAS_PUNTOS` = 70 points per coin) come from the balance tool and want playtesting (target: ~20 runs for an average player to finish the campaign; the whole tree costs 39 250 coins (about 59 runs for the average profile, 40 for the skilled one, per the tool); the campaign is beatable with roughly the first 10 % of it, the rest is long-term power).

**Real health and damage numbers.** Health and damage are real numbers, not "points": the ship has `Jugador.CONFIG["salud_max"] = 50` health, its bullet does `danio_base = 10` (cap `danio_max = 30`), an enemy bullet 10 (`DANIO_BALA_TIPO2/3`), the boss's heavy cannon 20 and fast one 10, contact 10 (`DANIO_CONTACTO`) and the enemy loses `DANIO_EMBESTIDA = 10` in the same collision; enemy `SALUD_BASE` is 10 / 20 / 30 at level 1. These numbers came from the old "points" system ×10 (a step that was checked to leave the game unchanged, frame-for-frame on seeded runs) and were then re-tuned by the rebalance. **Difficulty by level** lives in `src/core/escalado.py` (pure data + functions, one entry per campaign level): `VIDA_X` (multiplier on the normal enemies' `SALUD_BASE`: 1.0, 1.4, 2.0, 2.8, 3.8), `VIDA_JEFE` (the boss's actual health: 700, 1300, 2100, 3100, 4400) and `DANIO_X` (multiplier on every enemy bullet and on contact damage: 0.6 … 1.0, so level 1 is beatable with the bare ship). `escalado.vida_x/vida_jefe/danio_x(nivel)` clamp below 1; **above the last level** (endless waves) health keeps growing by the step between the last two entries and damage stays at the last value. `EnemigoBase.vida_en_nivel(nivel)` (a classmethod, `Jefe` overrides it) is the single source of an enemy's health, `EnemigoBase.danio_x`/`danio_escalado(base)` scale a damage number (rounded, never below 1) — used by every `disparo_*` and by the contact hit in `CollisionManager`; the damage the enemy *takes* from the collision (`DANIO_EMBESTIDA`) does not scale. `Bonus.salud_extra` / `danio_extra` and the tree's nodes are in the same real units. Under the ship, `UIManager._dibujar_indicador_salud_nave` draws a health **bar** (a fixed `ANCHO_BARRA_SALUD` = 48 px whatever the max health — with the full tree it is 100 and a proportional bar overflowed the screen edges —, a dark mark every `SALUD_POR_MARCA` = 10 health but at most `MARCAS_MAX` = 4, and its x is clamped inside the screen so it is fully visible with the ship at an edge); the HUD's stat bars use the same ratios as before.

**Balance tool** (`tools/balance.py`, a development script, not part of the game; `python tools/balance.py [--perfil medio|torpe|habil|todos] [--builds 0,25,50,75,100] [--niveles]`): an **analytic model** of the campaign that reads the game's real data (`niveles.NIVELES`, the enemy classes' class attributes `SALUD_BASE`/`VALOR`/`VEL_Y`/`CADENCIA`/`CADENCIA_NORMAL`/`CADENCIA_RAPIDA`, `mejoras.MEJORAS`, `Jugador.CONFIG` incl. `vel_base`/`disparos_base`, and the `settings` damage constants) so it never drifts from the code. For a ship (`Nave`, from `nave_de(ids)`) and a level it estimates the *afluencia* (enemy health entering per second ÷ the DPS you land; >1 means they pile up), the boss's time-to-kill, the expected damage from bullets/contact/boss and therefore the expected deaths (= damage ÷ max health), plus points and coins. `jugar()` plays a run level by level until the expected deaths use up the lives, `progresion()` chains runs spending the coins on the tree (cheapest available node first) to estimate how many runs the campaign takes, and `dps_necesario()` bisects the DPS a level demands. It cannot know how well someone dodges, so a `Perfil` (torpe / medio / hábil: accuracy, share of enemy bullets/contact/boss bullets that land, average combo) carries those **assumptions** — they are guesses, not measurements. A design proposal is a `Modelo` (`dataclasses.replace(MODELO_ACTUAL, vida=..., danio_x=..., arbol=...)`) with the level's `definicion`, `vida(clase, nivel)`, per-level enemy `danio_x(nivel)`, the tree and the ship builder as swappable pieces (to try a change before applying it, `replace` the piece and compare). `tests/test_diseno_balance.py` encodes the agreed design goals as tests against the real game (first run never wins, level 1 beatable unassisted, full tree wins for every profile, ~20 runs for the average player, no long waits between purchases): retuning a number that breaks one means deciding whether the goal or the number changes. `tests/test_balance.py` pins the model's formulas to the real game (enemy/boss health per level, base and full-tree ship) and **validates it against real play** (boss time-to-kill and enemy spawn rate measured in a real `Juego`).

**Score combo** (`src/core/combo.py`, pure, no pygame): `Juego.combo` is a `Combo` whose `racha` counts kills in a row without taking damage and whose `multiplicador` is `1 +` the number of `settings.COMBO_UMBRALES` reached (`(10, 25, 50, 90)` → ×2…×5, the last being the cap); it never expires with time, it only breaks on damage. `Juego.al_eliminar_enemigo` calls `combo.sumar_baja()` *before* scoring, so the kill that crosses a threshold already scores with the new multiplier: `puntuacion += valor_puntuacion * nivel * multiplicador` (the boss counts too). It is broken in `manejar_impacto_jugador` only when the hit really lands (not while invulnerable — same condition as the shake) and always when a life is lost; a contact kill therefore breaks the streak and then counts as the first kill of the next one. It **survives** a campaign level advance and an endless-mode wave/boss change (`reiniciar_juego` only breaks it on the full-restart and level-select paths, next to `puntuacion = 0`). `UIManager._dibujar_combo` draws "COMBO ×n" (`hud.combo`) with a progress bar to the next step under the score (under the wave label in endless mode), only from ×2 up, greyed out while paused. Balance values are first-pass.

**Saved game** (`src/core/guardado.py`, pure; `Guardado(modo, ruta=None, persistir=True)`, one per mode built in `main.py` and shared with `MenuManager(..., guardados)` and every `Juego(..., guardado=, continuar=)`): it is a **checkpoint, not a snapshot** — `{"version", "modo", "nivel", "puntuacion"}`, the level (campaign) or wave (endless) to continue at plus the score you had when you reached it. It is written when a campaign level is finished (`_finalizar_transicion_fin_de_nivel` saves `nivel + 1`, so it already counts if the game is closed on the level-complete screen) and on every endless wave change (`_avanzar_oleada`, which also covers a boss dying), through `Juego._guardar_punto_de_control`. **It is kept when you lose all lives, quit or crash** — the point being that an advanced player doesn't replay the easy early levels — and is only deleted by "Nueva partida" (`main.py`) or by completing the campaign (`guardado.borrar()` on the final victory). `guardar_punto` **never goes backwards** (replaying a cleared level from the level-select screen doesn't lower it) and clamps to `NIVEL_MAX` in the campaign. Continuing (`Juego(continuar=True)`) sets `nivel`/`puntuacion` from it and starts with a *new game's* lives and full health and no combo; `monedas_cobradas` is set to the coins those points already paid (`_monedas_de`), so they aren't paid twice. In the menu, `_empezar(modo)` asks with `_dialogo_partida_guardada` (Continuar (Nivel N / Oleada N) / Nueva partida / Volver) only when a save exists for that mode; the pause's throwaway menu has no `guardados`. Loading is tolerant like `Progresion`: a broken/ill-typed/out-of-range file or one from another mode is copied to `.corrupto` and ignored; writes are atomic.

**Endless mode** (`Juego(modo=settings.MODO_SIN_FIN)`; `src/core/sin_fin.py`, pure): `Juego.nivel` is the **wave number** (so score ×`nivel` and enemy health scaling work unchanged) and `inicio_juego` the start of the current wave. `sin_fin.definicion_oleada(n)` returns a normal `DefinicionNivel`, so `WaveManager.spawn_enemigo(..., definicion)` reads it like a campaign level (the `definicion` argument defaults to the campaign's, which is why the campaign path is untouched): a normal wave has `tiempo_jefe_ms = math.inf` and lasts `OLEADA_MS` (45 s), after which `_gestionar_generacion_enemigos` calls `_avanzar_oleada()` (heals — `SIN_FIN_CURACION_OLEADA` of max health, all of it after a boss —, bumps `nivel`, resets `inicio_juego`, the spawn interval, `WaveManager`'s boss flags and the music — nothing on screen is touched); every `JEFE_CADA`-th wave has `tiempo_jefe_ms = 0`, so the boss comes right after `ESPERA_JEFE_MS` with no other enemies spawning, and the wave ends when the boss dies (`al_eliminar_enemigo` clears the boss bullets and calls `_avanzar_oleada()` directly: **no** `transicion_activa`, level-complete screen, level select or victory in this mode). The spawn interval drops `INTERVALO_PASO_MS` per wave down to `INTERVALO_MIN`; there is no cap on health scaling. Reintentar (`reiniciar_juego()`) goes back to wave 1 (the campaign retries the same level). Game Over shows the wave reached (`game_over.oleada`), the HUD draws `hud.oleada` under the score, and the name-entry path saves `nivel=self.nivel` (= wave) in the endless ranking. The Puntuaciones screen has Campaña / Sin fin tabs (`MenuManager._modo_puntuaciones`, drawn by `_dibujar_pestanas_puntuaciones`; the ranking is read *after* processing events so a just-clicked tab draws its own rows), always opening on the campaign one. Values are first-pass and want playtesting.

**Campaign (fixed `settings.NIVEL_MAX` levels)**: killing the boss (`Juego.al_eliminar_enemigo`) sets `jefe_derrotado` + the deferred `pendiente_reinicio`, processed at the end of `actualizar()` by `_iniciar_transicion_fin_de_nivel()` — `reiniciar_juego()` isn't called until the player clicks through the resulting screen. That method swaps to `victory_tune`, empties `entity_manager.balas`/`balas_enemigo` (bullets don't linger through the transition or the overlay) and `disparando = False`, then sets `transicion_activa = True` / `transicion_fase = "centrar"`. While `transicion_activa`, `actualizar()` takes a **separate branch**: `_actualizar_transicion_nivel(dt)` scripts the ship instead of reading input (`InputHandler` also blocks Esc/Space/F1/clicks while `transicion_activa`, and the final `disparar()` guard checks it too) — `"centrar"` slides `jugador.rect.centerx` to mid-screen at `settings.TRANSICION_VEL_LATERAL` px/frame-60fps (Y untouched), `"subir"` then moves it straight up at `TRANSICION_VEL_SUBIDA` until `rect.bottom < 0`, ramping `background.velocidad` from `FONDO_VELOCIDAD_NORMAL` up to `× TRANSICION_FONDO_ACELERACION` over `TRANSICION_FONDO_RAMPA_MS` ms, and `"espera"` just waits `TRANSICION_ESPERA_MS` ms. `pausado` stays **False** the whole time (so `actualizar()` keeps being called at all — `Juego.ejecutar()` skips it entirely when `pausado`); `entity_manager.actualizar` keeps running too (so the boss's explosion finishes naturally) but `collision_manager` and enemy spawning are skipped (nothing left to collide with). `_finalizar_transicion_fin_de_nivel()` ends the sequence, resets `background.velocidad`, sets `pausado = True`, and:
- below `NIVEL_MAX` → `estado_nivel_completado = True` (its own overlay: stats for the level just cleared — `puntuacion`, `enemigos_eliminados_nivel`, `tiempo_juego` — with **Continuar** → `reiniciar_juego()` and **Elegir nivel** → `mostrando_seleccion_nivel = True`, a list of buttons for levels `1..min(nivel+1, NIVEL_MAX)`: the cleared ones *plus* the next one (labeled "(siguiente)"), session-only, no cross-run persistence — `RenderManager._dibujar_pantalla_seleccion_nivel` builds it, `settings.NIVEL_MAX`-aware). Picking a cleared level replays it from scratch (`reiniciar_juego(nivel_forzado=n)` — fresh `Jugador`, `puntuacion` zeroed); picking the next one is **the same path as Continuar** (`InputHandler._clic_seleccion_nivel` special-cases `nivel == juego.nivel + 1` to call plain `reiniciar_juego()`) so it keeps upgrades and score instead of resetting them.
- at `NIVEL_MAX` → `_pedir_nombre_o_mostrar("victoria")`, shared with `juego_terminado()`'s Game Over path (`"game_over"`): both funnel through the same top-10 check (`_cualifica_para_el_top10`) and `pidiendo_nombre_para` remembers which overlay (`estado_game_over` vs `estado_victoria_final`) to show once the name is entered (`InputHandler`'s `K_RETURN` handler branches on it, and now also passes `nivel=self.juego.nivel` to `agregar_puntuacion`). The final screen (`estado_victoria_final`) offers **Jugar de nuevo** (`reiniciar_juego(nivel_forzado=1)`) and **Menú**.

All the transition's speeds/timings are tunable constants in `settings.py`: `TRANSICION_VEL_LATERAL`, `TRANSICION_VEL_SUBIDA`, `TRANSICION_FONDO_ACELERACION`, `TRANSICION_FONDO_RAMPA_MS`, `TRANSICION_ESPERA_MS`, plus `FONDO_VELOCIDAD_NORMAL` for the baseline scroll speed.

The three post-transition states (`estado_nivel_completado`, `mostrando_seleccion_nivel`, `estado_victoria_final`) behave like `estado_game_over`: `InputHandler` checks them **before** the generic pause-click branch (same buttons-only, keyboard-inert treatment — see `_manejar_teclas_presionadas`'s guard), and `RenderManager` treats them as `overlay_propio` (no world entities drawn, own background+buttons, excluded from the pause fast-path). Their buttons are created lazily and cached on `juego` (`boton_continuar`, `boton_elegir_nivel`, `botones_seleccion_nivel` — a list rebuilt when `nivel` grows, `boton_reintentar_final`, `boton_menu_final`), same pattern as the Game Over buttons. `transicion_activa` is **not** one of these overlay states (`pausado` stays `False` while it runs, on purpose — see above) — it gets its own, separate guards in `InputHandler` and its own early-return branch in `Juego.actualizar()`; `RenderManager` needs no special case for it since the normal draw path (entities + player + HUD) is exactly what should be visible while the ship flies off.

`MenuManager` runs a background update check on entry: `src/core/updates.py` (`ComprobadorActualizaciones`) hits the GitHub "latest release" API in a daemon thread, compares `tag_name` to `__version__`, caches the answer (incl. the `*-setup.exe` asset URL and its SHA-256, read from the `digest` field GitHub adds to every Release asset) in `%APPDATA%` for 6 hours (`updates._CACHE_TTL`), and is fully best-effort (any failure → silent, no banner). If a newer version exists, `_menu_principal` shows a banner + `btn_actualizar`:
- **frozen** + installer asset **with a SHA-256** → `DescargaActualizacion(url, sha256)` downloads the setup in a thread (banner shows `%`) hashing it as it goes; on a mismatch it deletes the file and reports `error` (so it never gets launched — the banner falls back to "open the web"). If the Release has no usable digest, `_pulsar_actualizar` doesn't auto-install at all and opens the web instead (fails closed). This guards against corrupted/altered downloads, not a compromised GitHub account (hash and file come from the same place; only code signing would fix that). On success `lanzar_instalador` runs it `/SILENT` and the menu returns `"SALIR"`. `installer.iss` (Inno Setup, per-user, `AppId` fixed for in-place upgrade, `CloseApplications=yes`) closes the game, replaces files, and its `[Run]` entry relaunches it. User data in `%APPDATA%` is untouched. While a download is in progress (`_descargando_actualizacion()`), `_menu_principal` ignores clicks on every other button (Jugar/Opciones/Puntuaciones included) so leaving the menu can't abandon it mid-way.
- otherwise (running from source, or download failed) → opens the releases page in a browser.
Env var `GG_SIN_COMPROBAR_ACTUALIZACIONES` disables the check (set in `tests/conftest.py`). `build.yml` publishes the `.zip` and the `-setup.exe` on every Release.

**Opciones tabs.** The options screen is split into tabs — `menu.PESTANAS = ("controles", "idioma", "audio", "pantalla")` (display order; the first is the one Opciones opens on), each also the suffix of its text key `opciones.<name>` — built in `_inicializar_interfaz_opciones`. Each tab is a list of `pygame_gui` elements in `self._elementos_pestana[name]` and `_mostrar_pestana(name)` `show()`s the active one and `hide()`s the rest (hidden elements get no clicks, which matters: the hidden "English" button sits right on top of the music slider) and marks the active tab button with `.select()`. Guardar/Volver are outside any tab and act on everything touched in any of them (one snapshot, see above). `_abrir_opciones()` always resets to the first tab; rebuilding the UI after a language change keeps the current one (`_preparar_ui_opciones` ends by re-applying `self._pestana`). Switching tabs cancels a half-finished key rebind, and the key-conflict warning is drawn only on the Controles tab. Elements added to the screen must be registered in a tab's list or they'll never be hidden.

The `pygame_gui` options screen uses the 0.6+ event API (`event.type == pygame_gui.UI_BUTTON_PRESSED` / `UI_HORIZONTAL_SLIDER_MOVED`), not the old `USEREVENT` + `event.user_type`. `MenuManager` keeps a single `self.clock` (only the outer loop `tick`s) and a single `self.ui_manager`, built lazily once by `_inicializar_interfaz_opciones` and re-synced on each entry by `_abrir_opciones`. Volume handling for **both** sliders: dragging the bar is free (`UI_HORIZONTAL_SLIDER_MOVED` → `_clamp_volumen`, just `[0,1]` + round to 2 dp); an ◄ ► arrow click sets `_flecha_pendiente = (destino, sube)` on `UI_BUTTON_PRESSED`, and **after** the event loop (same frame, before drawing) the value is snapped to the multiple of `VOLUMEN_PASO` just above/below the previous value (`_paso_volumen`, so `0.25` → `0.3`/`0.2`) — pygame_gui has already applied its own `±increment` during `process_events`, and correcting it in-frame avoids a one-frame visual jump. The `MOVED` pygame_gui then posts is ignored next frame via `_ignorar_moved`. Every applied value is pushed back with `set_current_value` — a value outside `[0,1]`, even by `1e-17`, makes `pygame_gui` silently freeze the slider. `button_held_repeat_acc` is zeroed on any held arrow so pygame_gui's hold-to-fast-scroll never kicks in (it made the volume visibly overshoot before settling).

### Entities

`ResourceManager` (`src/core/resources.py`) is a `__new__`-based singleton. `load_image` runs `.convert()` / `.convert_alpha()` at load (so blits don't convert per-frame). `get_image_scaled` caches by `name_WxH`; `get_image_rotated(name, size, angle)` caches by `name_WxH_r<deg>` — projectiles now get a ready-made oriented `Surface` from here instead of loading/scaling/rotating per bullet. `get_image_path` still exists for other callers; `get_music_path` / `load_music` register music paths without decoding.

Enemies (`src/entities/enemies.py`): `EnemigoBase` → `EnemigoTipo1/2/3` and `Jefe`. Health and damage scale by the per-level tables in `escalado.py` (`vida_en_nivel`, `danio_escalado`). **Enemies drop nothing**: there are no in-run pickups any more (power-ups and healing items were removed), so the ship's power comes only from the permanent upgrades. `Jefe` also overrides `movimiento_enemigo` (no-op) and drives its own patrol in `update`. The `disparo_*` methods take `(ahora, rm, nombre_bala)`, read damage/speed from `settings`, and build the projectile through `rm.get_image_rotated`.

Projectiles: `src/entities/base/projectile_base.py` (`Proyectil`, which mixes in `MovimientoSubpixel`) is the shared base for `Bala` (`bullet.py`) and `BalaEnemigo` (`bullet_enemy.py`). **They receive a cached `Surface`, never a path** — no disk I/O per shot, no per-instance rotate. Size/orientation constants: `Bala.TAMANO`/`Bala.ANGULO`, `BalaEnemigo.TAMANO`. Collision is `collide_circle` on `radius`, set per class from `RADIUS` (`settings.RADIO_*`). Every `update(self, dt=0)` and `Jugador.mover(teclas, pantalla, dt)` takes `dt`. `Jugador.mover` normalizes the diagonal and applies optional smoothing (`settings.JUGADOR_SUAVIZADO`). Player stats (damage, `disparos_s`, `balas_por_disparo` 1–3, speed, `regen_s`) live on `Jugador` (`src/entities/player.py`) and only the permanent upgrades (`bonus`) change them; **invulnerability** (the 3 s shield after losing a life) is the `invulnerable` flag *plus* a `DestelloConstante` halo sprite in `entity_manager.efectos` referenced by `jugador.destello_constante`, and the two must end together through `Jugador.terminar_invulnerabilidad()` (used by `update`, `reiniciar` and `reiniciar_juego`) — never by flipping the flag alone: a level advance keeps in-flight effects, and `update` only removes the halo while `invulnerable` is true, so a stray halo would stay on screen forever. Without healing items, health comes back at each campaign level advance (`reiniciar_juego`), on each endless wave change (`_avanzar_oleada`: `SIN_FIN_CURACION_OLEADA` of max health, full after a boss) and when a life is lost.

**F1** toggles `juego.debug_hitboxes` → `RenderManager._dibujar_hitboxes` draws the real collision circles.
